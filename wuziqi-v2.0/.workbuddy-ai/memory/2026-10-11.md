# 2026-10-11

## 排查「局域网联机连不上」问题（未改代码，仅诊断）

用 Playwright（chromium-1248，两个独立浏览器进程）实测复现了完整握手流程。

**实测证据**
1. 同机双实例跑完整「邀请码 → 回传码 → 确认连接」流程：519ms 建连成功，无 pageerror
   → 说明 `utils.js` 信令编解码、`peer.js` offer/answer 流程本身是**正确**的。
2. 打印邀请码 SDP：只有 **1 个候选**，且是 `e07d8db6-....local` 形式的 **mDNS 混淆主机名**，
   不是真实内网 IP。`config.js` 中 `ICE_SERVERS: []`，没有任何 STUN/TURN 兜底。
3. 加 `--disable-features=WebRtcHideLocalIpsWithMdns` 重启后，候选变为真实内网 IP
   `172.17.44.192` → 证实默认情况下 Chrome 会把 host candidate 藏成 `.local` 名。

**根因**
Chrome 在页面未获得媒体权限时，会把 host candidate 用 mDNS 混淆成 `.local` 名。
同机回环时浏览器能自己解析自己的 `.local`，所以能连；两台真机必须靠**多播 DNS** 解析
对方主机名，一旦路由器开 AP 隔离 / 屏蔽多播 / 跨网段 / 跨浏览器，解析失败 → 无候选对
→ 一直停在「连接中…」直到 failed。
README 中「局域网不需要 STUN，host candidate 可直连」的说法对现代 Chrome 已过时。

**附带发现的次要问题（放大症状）**
- `app.js` `_onPeerState` 在 `connection === 'failed'` 时调 `_showBanner()`，但 banner 的
  DOM `#board-banner` 位于 `#view-game` 内部，而失败时用户还在 host/guest 视图，
  `.view { display:none }` → 实测 `bannerActuallyRendered: false`，**用户看不到任何提示**。
- `app.js` `_hostAcceptAnswer` 成功分支从不恢复 `#btn-accept-answer` 的 `disabled`，
  状态文案停在「握手完成，正在打通数据通道…」，按钮永久变灰 → 表现为「界面卡住无反应」。
  与 docs/REVIEW_CHECKLIST.md C 项「连接失败要有用户可见提示」相矛盾。

**建议修复方向（待用户确认后再动手）**
1. `ICE_SERVERS` 填入 STUN（关键）：如 `stun:stun.qq.com:3478`、`stun:stun.miwifi.com:3478`。
2. 握手失败/超时的提示打到当前视图（inline-status 或 toast），并恢复按钮可用。
3. 加握手超时（约 10s 未 open 即判失败）。
4. 真机排查用 `chrome://webrtc-internals` 看候选与 candidate pair。

## 修复 #1：给 ICE_SERVERS 配上 STUN（已改代码 + 已回归）

改 `js/config.js`，`ICE_SERVERS` 从 `[]` 改为 3 个**实测可达**的公共 STUN：
`stun.miwifi.com:3478`、`stun.chat.bilibili.com:3478`、`stun.hitv.com:3478`
（首个 srflx 约 40~50ms，收集完成约 130ms）。

**批量探测结果（重要）**
| 服务器 | 首个 srflx | 收集完成 |
|---|---|---|
| stun.miwifi.com:3478 | 49ms | 136ms |
| stun.chat.bilibili.com:3478 | 49ms | 120ms |
| stun.hitv.com:3478 | 42ms | 122ms |
| stun.douyucdn.cn:18000 | 31ms | 138ms |
| stun.l.google.com:19302 | 184ms | 184ms |
| **stun.qq.com:3478** | **无响应** | **永不完成** |
| **stun.syncthing.net:3478** | **无响应** | **永不完成** |

坑：只要列表里有任何一个不响应的 STUN，`iceGatheringState` 就永远停在
`gathering`，每次生成邀请码都要干等到 `ICE_GATHER_TIMEOUT` 才截断。
实测混入 `stun.qq.com` 后生成耗时从 0.6s 涨到 3.8s 且后续候选被丢弃。
**结论：只填实测能响应的服务器。**

**回归结果（Playwright 双浏览器进程）**
- 邀请码含 `srflx` 候选 ✅（真实公网地址）
- 打包时 `iceGatheringState = complete`，候选未被截断 ✅
- 生成邀请码耗时 ~1.4s（原 0.6s，STUN 的代价，可接受）
- 完整回归 **10/10 通过**：握手 305~512ms、双方进入棋盘、连接状态显示已连接、
  落子同步一致、聊天送达、无 pageerror
- 同机时 ICE 实际选中的仍是 `host <-> host`（mDNS 解析成功），
  `srflx` 是备用路径 → **真机双设备效果本机无法验证**，需实机确认

## 复现「Called in wrong state: stable」（用户提供的历史截图报错）

用户以为是自己环境问题。**实测证明这是信令状态错误，与网络无关**，
在当前项目里可 100% 复现（全程不需要网络：直接把挑战者浏览器关掉）。

复现步骤（真实 UI 路径即可走到）：
1. 房主生成邀请码 → 粘贴回传码 → 点「确认连接」
2. 若 ICE 没打通（如 mDNS 被挡），房主仍停在创建房间页，
   但 `pc.signalingState` 已由 `have-local-offer` 变成 `stable`
3. 点「返回」→ 再进「创建房间」→ **旧连接没被释放（仍 alive）、
   「确认连接」按钮被 `_resetHostView()` 重新启用**
4. 再点一次「确认连接」→ 报
   `Failed to execute 'setRemoteDescription' ... Called in wrong state: stable`

**代码层根因**
- `app.js` `_startHost()` / `_resetHostView()` 不复位连接对象
- `Views.setGuard` 只拦 `from === 'game'`，从 host/guest 视图点「返回」直接放行、不做清理
- `peer.js` `finishWithAnswer()` 未校验 `pc.signalingState`，也未给出可读提示
- `_hostAcceptAnswer()` 成功分支不恢复按钮，但 `_resetHostView()` 会重新启用 →
  「旧 pc + 可点按钮」必然触发

当前项目 UI 提示原文（把原始英文异常直接透给了用户）：
`连接失败：Failed to execute 'setRemoteDescription' on 'RTCPeerConnection': Failed to set remote answer sdp: Called in wrong state: stable。请确认回传码完整复制。`
（截图里是「确认连接失败: …」且无后半句，确认截图来自用户另一个项目。）

**两类失败要分清**
- 网络被挡（mDNS / NAT）→ 停在「连接中…」最后 failed，**没有红字报错**
- 流程/状态错乱（重复用同一段回传码、中途刷新、重新生成邀请码后仍用旧回传码）
  → 红字 `wrong state: stable`

待办：修复 #2（失败提示打到当前视图 + 恢复按钮）、#3（握手超时），
以及上面这条「重新进入创建房间页应释放旧连接」。

## 已完成：联机建连可靠性修复（4 个问题）

**改动文件**：`js/config.js`、`js/peer.js`、`js/app.js`、`README.md`、
`index.html`（FAQ）、`docs/REVIEW_CHECKLIST.md`（新增修复记录 19~23）

### #19 网络层：ICE 候选只剩 mDNS 名
`ICE_SERVERS` 从 `[]` 改为 3 个实测可达的公共 STUN（miwifi / bilibili / hitv）。
README「局域网不需要 STUN」一节改写为准确说明。

### #20 失败提示不可见
新增 `_failHandshake(text)`：把提示写进**当前页**的内联状态 + Toast，并恢复按钮。
`_onPeerState` 改为：仅在 `GM.Views.inGame()` 时用 `_showBanner`，否则走 `_failHandshake`。

### #21 按钮卡死 + 无超时
`_hostAcceptAnswer` 成功分支立即恢复按钮；新增握手看门狗
`_startHandshakeTimer(limit)`，配置项 `CONFIG.HANDSHAKE_TIMEOUT`（房主 15s）与
`CONFIG.HANDSHAKE_WAIT_HOST`（挑战者 90s）。`_clearHandshakeTimer()` 在
`_teardownLink` / `_onChannelOpen` / `_resetXxxView` 中调用。

### #22 旧连接残留导致 `wrong state: stable`
`_startHost` / `_startGuest` 与 `Views` 守卫（`from === 'host' | 'guest'`）都调用
`_teardownLink()`。守卫原本只拦 `from === 'game'`。

### #23 英文异常直透用户
`peer.js` `finishWithAnswer` 前置校验 `pc.signalingState === 'have-local-offer'`，
否则抛中文；`app.js` 新增 `_readableError(err)` 翻译 `wrong state` / `sdp|ice|dtls`
类英文异常，并在 4 处 catch（生成邀请码 / 生成回传码 / 确认连接）统一使用。
